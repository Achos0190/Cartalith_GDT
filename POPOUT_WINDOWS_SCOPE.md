# POPOUT_WINDOWS_SCOPE.md — popping panels out to a second monitor

**What this is:** research and a proposed scope for one owner question (2026-10-26): *"can we pop out screens (planner, civilisation screens) to a second monitor?"* It **defines** milestones and bars and carries no status column (progress is `cartalith-native/docs/STATUS.md`). **Owner answers to Q1-Q7 are recorded in Ruling DK (2026-10-25) and marked in section 7; the feature is scheduled, first milestone PW-0.** **Nothing is built; PW-0 (section 8) is measured, 2026-10-26**; every other number is a bar to be met. Evidence tags: **[verified]** opened in the repository at the symbol named; **[cited]** read in the Godot class reference on 2026-10-26 (`docs.godotengine.org/en/stable/classes/class_window.html`, `class_displayserver.html`; the stable docs, not specifically 4.7); **[recalled]** from memory, not re-checked; **[judgement]** a labelled recommendation the owner may overrule. Read `MISTAKES.md`'s preflight first. The rows that bite: *Write a test that pins a constant*, *Read a layout that overflows the screen*, *Claim something covered is now visible* (flip the flag, diff the framebuffer), *Run a pixel probe* (windowed, never headless), *Declare the work green* (`cargo test --workspace` plus parse-check every touched `.gd` and `shell/app.gd`).

**Short answer.** Yes on desktop, and cheaply for the civilisation windows; harder for the planner; not on Android. Almost every "screen" the owner means is already a Godot `Window` (an `AcceptDialog`) that is merely *embedded* in the main window, so a pop-out is mostly a property flip plus the places that assumed embedding. The planner is **not** a window: it swaps the main view, and popping it out is a re-hosting job. The project's renderer (`gl_compatibility`) is the one thing worth measuring before promising.

## 2. Godot facts that decide the design

1. **A `Window` is native or embedded.** The class reference says a window "can either be a native system window or embedded inside another Window (see `Viewport.gui_embed_subwindows`)" [cited]. `Window.force_native`: "If `true`, native window will be used regardless of parent viewport and project settings" [cited]. So a per-window pop-out needs no global change: set `force_native = true` before the window is shown, or flip `gui_embed_subwindows` on the parent viewport for all dialogs at once. The project-wide switch is `display/window/subwindows/embed_subwindows` [recalled].
2. **Placement.** `Window.current_screen` is "the screen the window is currently on" [cited]; `DisplayServer.get_screen_count()`, `screen_get_position/size/usable_rect/dpi/scale(screen)` all exist [cited, signatures only]. `FEATURE_SUBWINDOWS` is "Display server supports multiple windows that can be moved outside of the main window" and the reference lists it for Windows, macOS and Linux (X11) [cited]. **Android is not in that list**, so on a phone a window can only be embedded [judgement from the list; confirm on the device in PW-5].
3. **Theme.** `Window.theme` merges with a child's own theme, child wins [cited]. A `Window` is its own theme root only when it carries a theme or inherits from the nearest parent `Control`/`Window` [recalled: native windows are *not* children of a `Control` in the render sense, but they do inherit `ThemeDB` project theme; whether the `gui/theme/custom` dark theme reaches a native window must be measured]. **"Window styles will have no effect unless the window is embedded"** [cited]: the title-bar/border `StyleBox`es the DCC theme draws for embedded dialogs (`embedded_border`, `embedded_unfocused_border`) are replaced by the OS frame when native, so the pop-out looks different by design; the contents are ours. **Measured in PW-0: the dark DCC theme does reach a native window (3 of 3 pixel samples equal the embedded case).**
4. **Content scale.** Each `Window` has its own `content_scale_factor`/`content_scale_mode` [cited for the factor]. `DccWidgets.phone_present` already sets these per dialog [verified]. A native window on a monitor with different DPI will need its own factor (`screen_get_scale`/`screen_get_dpi` of *its* screen), which the main window's cannot supply.
5. **Input.** A native window is its own viewport and receives its own events (`window_input` is emitted when "the Window is currently focused" [cited]). Key events typed in it will **not** reach `DccApp._unhandled_key_input` [**measured by event delivery in PW-0**, section 8; the real-OS-keystroke leg was inconclusive]. Ctrl+Z/Ctrl+Y/Ctrl+S in a pop-out therefore need an explicit forward (PW-2).
6. **Lifetime.** `transient` makes a window "a child of another Window ... destroyed with its transient parent and will return focus to their parent when closed"; `exclusive` "blocks all input going to the parent" and "needs transient enabled" [cited]. Pop-outs must be **transient and non-exclusive** (the point is to use both screens at once). `close_requested` is "emitted when the close button is pressed"; "windows will not close automatically when requested" [cited], so the existing `AcceptDialog` close wiring is the pop-out's close path.
7. **Renderer.** `gl_compatibility` is the renderer for desktop and mobile in this project [verified]. A native sub-window gets its own surface; its per-frame cost under `gl_compatibility` is **measured in section 8** (+1.2 ms per frame for one window and +1.7 ms for three at a continuous redraw, nothing at idle).
8. **GPU selection interplay.** Ruling DF's low-power compute adapter is unrelated to the display adapter; a second monitor on the *other* GPU is a Windows concern, not ours (`LLM_ASSISTANT_SCOPE.md` s.5a).

## 3. Shared state, undo and the busy overlay

- **One process, one SceneTree, one `EngineBridge`.** Every window shares the same engine state, so no synchronisation layer is needed [verified: `setup(self, bridge)` for every window]. The risk is *assumption*, not data: code that reaches the main window by `get_window()` or `get_viewport()` now gets the pop-out [verified call sites: `markdown_editor.gd` `anchor_rect` uses `c.get_window()`; `DccWidgets` popups use `get_viewport()`].
- **Undo.** There is one undo surface, `DccApp.can_undo_any()`/`redo_last()` over the height stack and `LookHistory`; it is reached by accelerator or menu from the main window. A pop-out that edits (the roster edits factions) must still push to the same stack; this is already true because it calls the bridge. What breaks is the **accelerator**: forward unhandled key events from a pop-out to `DccApp` (a three-line handler in a shared base, not per window).
- **Busy overlay.** `BusyOverlay` mutes *embedded* subwindows and draws a card mirror into them; it does **not** know native windows [verified: `get_embedded_subwindows()`]. A native roster left open during a generate would stay clickable and could write the engine. Gate: during a run every pop-out is input-disabled (`Window.gui_disable_input`) and shows the card mirror, or the pop-out is hidden. This is the highest-risk item and PW-2's first bar.
- **Generation-time read gates** (`_gsw_probe`, the engine-call sweep in `OUTSTANDING_WORK.md` §2.10) apply to a pop-out exactly as to the embedded window; no new gate needed.
- **Window geometry** is per-device UI state: stored in `DccSettings` beside the other UI state, never in a project, export or archive (the quick bar's Q7 precedent, Ruling DH).

## 4. Design

**Setting.** `Preferences ▸ Windows ▸ Open panels in their own window` (`[windows] popout`, default **off**; Ruling-level default is the owner's to confirm, Q1). Off means every window is built and shown exactly as today, with **zero** native windows; the code path is not entered. On means the listed panels open with `force_native = true`, `transient = true`, `exclusive = false`, on the screen they were last closed on (clamped to an existing screen; see Q3). A per-panel "Pop out / Dock" item in each window's title row lets a user move one open window without the global setting. Owner, Ruling DK Q2: **both ship from the start**, so the button is part of the pilot (PW-2), not a later milestone.

**Scope order.** (1) **Pilot: `FactionRosterWindow`, with the global setting and the per-window button together** (the biggest, 4 043 lines, most used for a second-monitor reference while the map stays on the first; it exercises tabs, popups, colour pickers, the busy overlay and edits). (2) The other civilisation windows (settlement types, place editor, generation rules, city viewer). (3) Vault and Assistant windows. (4) **The planner**, as its own milestone, because it is a view swap. Data Manager, Asset Library and dialogs that block (`exclusive` file pickers) stay embedded.

**Planner.** Re-hosting `_left_panel` + `_center_panel` into a `Window` is feasible because both are built in `_build_left_panel`/the centre builder and parented only at `_show()`; the coupling that needs a decision is what stays on the main screen. Recommended [judgement]: in pop-out mode the planner's panels live in the native window, **the main window keeps its live map** (`app.viewport.visible` stays true: that is the whole benefit), the right dock's Journey section stays docked, and `timeline_row` stays in the main window. Costs: `_show()`'s swap becomes conditional; `_phone_refit` and `_recompute_visibility` assume one region; the planner draws its own route map (`_RouteMapView`), so the main map and the planner map both exist, doubling that texture's footprint [to measure]. If PW-4's measurement says this is large, the fallback is a planner pop-out that takes **only the stage table and profile**, with the route map left embedded.

**Not offered.** Android and iOS (no `FEATURE_SUBWINDOWS`): the setting is absent from the phone's MORE and shown disabled-with-reason on a tablet, per the `CommandIndex` rule (a reason beside every disabled control).

**Never changes.** Seed-deterministic generation, the save format, undo semantics, golden outputs. A world generated with the setting on equals one generated with it off (bar in PW-2).

## 6. Risks

1. **Busy-overlay hole (PW-2a):** a native window is outside the overlay's reach today. Mitigation is the first bar; if the mute cannot be made reliable, pop-outs hide during a run.
2. **Accelerators go dead** in a pop-out (key events do not reach `DccApp`). Mitigation: shared forwarder, bar (b).
3. **`gl_compatibility` cost** of extra native windows is unmeasured; PW-0 may show it is large on this renderer. Owner (Ruling DK Q7): **continue anyway**, record the numbers in PW-0 and `STATUS.md`; stop and report only if the cost makes the app unusable, i.e. fails an existing bar in `PERFORMANCE_BENCHMARKS.md`.
4. **Theme and chrome:** the DCC window chrome is drawn only for embedded windows; a native window has the OS frame. A dark-theme app with a light OS title bar is an owner-visible mismatch (Windows 11 follows the system theme [recalled]); it is inherent, not a bug.
5. **DPI mismatch between monitors** can leave one window blurry or tiny unless the factor is set per screen.
6. **Stale-geometry hazard:** restoring to a monitor that is gone strands the window off screen. Mitigation: PW-1's clamp table.
7. **Many windows × the single-instance assumption:** code that assumes one dialog is modal over the app (`exclusive`) would let the user edit the main map while a pop-out is mid-edit. The roster is already non-exclusive, so this is judged small; PW-2 states what was checked.
8. **Phone/tablet parity:** the three-shell rule (`DESIGN_HANDOFF.md`) is satisfied by the setting being desktop-only, and that must be written into the control index.

|---|---|---|---|---|
| 0 | 8.98 .. 9.02 | 0 | 8.99 .. 9.02 | 16.67 .. 16.74 |
| 1 | 10.17 .. 10.23 | **+1.2 ms (+13 %)** | 9.08 .. 9.15 (+0.1) | 16.67 .. 16.74 |

The draw span (`frame_pre_draw` to `frame_post_draw`) tracks the frame time to within 0.03 ms, so the cost is CPU draw submission, not waiting. The native cost is a **fixed per-window per-frame redraw**: about 1.2 ms for the first window and about 0.25 ms more for each of the next two here. An embedded window costs a tenth of that because it shares the main window's one pass. After closing every window the baseline returns (8.98 .. 9.08). **Under vsync the app is at 16.67 ms with 0, 1 and 3 native windows**, so at 60 Hz the frame time did not move.

**Idle (the shipped low-processor mode, 5 s, no input):** 0 frames drawn with 0, 1 and 3 native windows open, so an idle native window costs no redraws; process CPU 0.3 to 2.3 % of a core with no trend by window count across four runs, which is the resolution of the method (two PowerShell reads of `TotalProcessorTime`), so **no idle cost is resolvable**. Not positively controlled in this probe (the `Engine.get_frames_drawn()` counter is the one `_idleredraw_probe.gd` validates).

**Open latency (`open()` to the second frame drawn, vsync on, 20 opens per mode, the first open of each block dropped):** embedded **92.2 .. 93.3 ms** (min 88.8, max 103.8), native **102.7 .. 105.2 ms** (min 99.9, max 110.3), four processes, two blocks each: a native open costs about **+10 to +12 ms**, with a floor of about two frames (33 ms) inside both figures.

**Memory:** `Performance` video memory rises **+4.3 MB for the first window and +13.2 to +15.7 MB for three** native windows (almost all texture), the same texture cost as embedded; the monitor never falls on close, so each figure is a delta against the same run's closed state just before opening. The embedded configurations also show a one-off canvas **buffer** step of +34 MB (one window, in the run where embedded came first) to +68 MB (three) that persists after close and lands in the main window's own buffers, not from native windows. Process private bytes rose about +12 MB (one native window) and +39 MB (three); working set flat (1533 to 1540 MB). **The GPU-process dedicated-usage counter (`GPU Process Memory`) was too noisy to resolve per-window VRAM:** baseline 1431-1445 MB, one window 1333 MB, three 1378 MB (it fell), so a swapchain cost is below its noise (about 100 MB); `Performance` does not count swapchains. VRAM per native window is therefore **not resolved**; the measured per-window texture cost is the +4 to +5 MB above.

**Bars from `PERFORMANCE_BENCHMARKS.md`:** its shell-facing bar is "0 % of tiles over a 60 Hz frame" (sections 5.4 and 5.5, tile synthesis) and its frame tables are engine concurrency measurements (sections 7.1 and 7.2); it has no bar on the per-frame cost of the shell's own draw. The only bar a native window could touch is the 60 Hz frame, and it held (vsync-on median 16.67 ms with 0, 1 and 3 windows). **No existing bar failed, so Ruling DK Q7's stop condition did not trigger and PW-1 proceeds.** The numbers are recorded in `STATUS.md`.

**What PW-0 changes for later milestones:** (1) PW-2's mute must be added for native windows: `get_embedded_subwindows()` is the only list the overlay walks. (2) PW-2 bar (b) cannot be shown by pushing events alone; it needs a real keystroke, which this probe could not inject. (3) A native window on a different-scale monitor must be resized when its factor changes. (4) The cost is per open native window per frame at a continuous redraw: hiding a pop-out the user is not looking at recovers it. (5) A pop-out can sit on screen 0 with the main window, so every single-monitor bar can be run on one monitor; only the multi-monitor ones wait for the owner.
