ONE ARITHMETIC, NO PROSE
Six rows and a total. Every line is a subtraction the pass actually performed, in the order it performed it, and each names the threshold it applied so the user can go and change that exact number. Nothing here is a sentence explaining the algorithm; the algorithm explains itself by showing its own working.
THE HIGHLIGHTED ROW IS THE ANSWER
The binding constraint is washed in accent and it is the only accent in the popover. Whatever else the funnel says, the eye lands on the line that produced the reason token in the row above, so the two agree by construction rather than by the reader's arithmetic.
“CAP · NOT REACHED” EARNS ITS ROW
It subtracts nothing, and it is the most important line here. It is the panel stating, in its own funnel, that the number the user set was not what limited them — which is the whole of the owner's “a maximum number does not mean that the maximum number of a certain type should be placed.” Omit it and the funnel silently drops the one term the user came to check.
TWO ACTIONS, BOTH SPECIFIC
Lower crowding to × 0.70 is computed, not offered as a gesture: it is the multiplier at which the 124 rejected candidates would have fit under the remaining cap. A generic “adjust spacing” would send the user back to guessing.

Show rejected draws the 124 as dashed markers inside the placed ones' exclusion rings — the state Dock.dc.html's viewport is already drawn in. Seeing the rings overlap is the moment the concept lands, and it needs no vocabulary at all.
WHAT THE ENGINE OWES THIS
Six integers and one threshold each. Nothing here needs a retained raster: the pass is counting its own rejections as it makes them. The division of labour is explain_settlement's — engine returns facts, shell writes the six labels — which is also why the labels can be reworded without touching Rust.
